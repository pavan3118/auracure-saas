# Database specification

## Status and invariants

**Approved/baseline:** MongoDB with strict tenant isolation; registration creates Tenant and Owner in one transaction; roles follow U04. The schema below is **ASSUMPTION - needs approval (A07)** in its entirety, except those explicit invariants. Field lists are a proposed minimum, not an approved clinical or legal record schema.

## Proposed collection catalog — ASSUMPTION - needs approval (A07)

All ordinary collections have `_id`, `tenant_id`, `created_at`, `updated_at` and an optimistic `version`. Tenant has `tenant_id = _id`; an initial ID is generated by the bootstrap service. Object IDs are identifiers, never authorization. Audit/ledger entries use append-only revisions rather than updates.

## Bootstrap and platform exceptions — ASSUMPTION - needs approval (A04, A06, A07)

`onboarding_challenges` is an isolated pre-tenant collection holding normalized contact/subdomain claims, hashed verification proof, expiry and attempt state. No patient data. Because no tenant exists yet, it cannot have a valid tenant_id. This is an explicit proposed exception to the master prompt's all-collections rule, not a hidden omission. On registration, consume the verified challenge atomically with creation or use a transactionally coupled single-use claim; generate tenant and owner IDs server-side.

`system_admins` and `platform_audit_events` are platform-scoped exceptions without tenant_id. SYSTEM_ADMIN is not a tenant user and has no routine clinical data access. MFA/recovery secrets are encrypted using a managed key service; passwords and low-entropy PINs are hashed with independent rate limiting. Exact encrypted-field/key handling needs provider approval.

## Isolation enforcement — ASSUMPTION - needs approval (A07)

A verified request context supplies tenant_id to mandatory scoped repositories. Enforce scope for find, count, update, delete, populate, aggregation, bulk operations and raw-driver escape paths. No unscoped repository is exported to normal controllers. Aggregation lookups match both tenant and resource IDs. Every referenced user/patient/visit is checked in the same tenant; MongoDB references alone do not enforce this.

PATIENT requests add `patient_id` from verified account linkage; clinical staff access follows permission and assignment rules. A matching resource ID in another tenant returns 404. Role denial returns 403. Tenant row queries are scoped to the authenticated tenant; unique subdomain enforcement uses the narrowly privileged bootstrap path.

## Atomicity and concurrency — ASSUMPTION - needs approval (A07, A10–A18)

Atlas deployment must support transactions. Registration uses one transaction and a unique index, not a pre-check alone. Queue claims use a conditional state update with deterministic ordering. Prescription writes compare version and lease ownership. Dispensing conditionally decrements all allocated batches and records dispensing in a transaction. Payments and wallet debits use durable unique keys and atomic balance rules; outbox delivery happens after commit. Provider retries may be at-least-once; database effects must deduplicate.

JWT issuance occurs only after successful commit. External messages/payments never run inside a database transaction. Driver retry behavior must not repeat non-transactional side effects. TTL cleanup is asynchronous, so every authorization checks expiry explicitly.

## Data lifecycle — ASSUMPTION - needs approval (A21)

No automatic deletion of clinical, financial or audit records until retention policy is approved. Short-lived challenges and sessions use TTL cleanup. Backups, restore exercises, encryption/key rotation and indexes are deployment gates. Never seed real healthcare records into development or tests. Store PDFs in private object storage, not public URLs or inline MongoDB blobs.

## Phase 2 schema mapping

Implementation uses the existing UUID/string-ID and tenant_id conventions. Patient stores name, normalized searchName, contactType/contactValue, optional dateOfBirth, linked userId (empty until check-in) and version. Unique tenant/contact and partial unique tenant/linked-user indexes prevent accidental account merging. Visits have patientId, optional doctorId, state, monotonic queueNumber, queuedAt, version, durable checkInKey/requestHash and cancellation metadata. A partial unique tenant/patient index allows only one QUEUED/IN_CONSULTATION visit. Tenant.queueSequence advances in the check-in transaction.

Vitals records store the exact approved observation codes/units, visit/patient IDs and recorder ID; they are append-only. CashSession stores receptionistId, openingFloatMinor (integer paise), INR, OPEN state and a durable operation reference; closing/payment movements remain unimplemented. Operation records are tenant/actor/operation/key unique, expire after 24 hours, and store request hashes/resource references rather than raw patient payloads. All resource creation, audit and retry writes are transactionally coupled. Apply additive indexes with the existing db:indexes workflow before serving Phase 2 traffic.

## Phase 3 schema mapping

New tenant-scoped collections: ConsultationNote (unique tenant/visit, versioned DRAFT → FINAL); NoteAmendment (append-only correction fields/reason/actor and unique operation reference); Prescription (unique tenant/visit/revision, one DRAFT per encounter, session-bound lease, signed content hash/time/actor or retained DISCARDED state); LabOrder and ServiceOrder (ORDERED only, durable operation keys); UsageEvent (unique tenant/meter/sourceId, quantity=1 encounter for completion). Visits add claimedAt/completedAt, claimKey and completion key/request fingerprint, plus a partial unique tenant/doctor index for IN_CONSULTATION.

Unsigned draft edits/sign/discard, note saves, order creation and completion serialize through the visit version. Clinical finalization and usage insertion are atomic. Signed revisions and finalized notes are immutable through exposed services; corrections append new records. No password or password-derived proof is copied into retry/audit records. Apply additive indexes before Phase 3 traffic.
